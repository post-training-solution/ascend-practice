# 昇腾训练实践文档模版

## 什么时候用

- 用户要写一篇新的昇腾训练实践或最佳实践文档。
- 用户给出旧文档、实验日志或聊天记录，要求按模版整理。
- 用户要求把一篇多场景文档按场景拆开。

## 基本规则

1. **一个场景一篇。** 场景 = 模型 + 序列长度 + 卡数 + 框架。同一模型的 258K 和 4096 要分两篇。
2. **不覆盖原文。** 重编排时新建文档，原文档保持不动。除非用户明确要求，否则不删除、不改写原文。
3. **只用源材料里的数字。** 不编造。推算出的值写明“推算，待确认”，估算值写明“估算”。
4. **缺什么写“待补”。** 章节和表格列保留，内容写“待补”，不要整节删掉。
5. **负收益和无收益的尝试也要列出来**，写清楚结论（例如“未采用”）。
6. **内容原则：可迁移。** 和本机环境绑定的值不要写进正文命令和表格：共享存储与挂载点路径（`/mnt/sfs_turbo` 这类换环境必然不存在的盘）、容器名、主机名 / IP、端口、个人或租户目录。在“环境依赖”里用一张变量表声明，正文只用变量，换环境只改这张表。初始状态可能只会有“场景” “环境依赖”。
7. **性能指标** 性能指标包含 单步耗时、有效TPS、MFU。
8. **核心目标** 旨在在特定场景+特定环境依赖的情况下，能够完成端到端的模型部署、精度对齐、性能摸高，帮助使用者少走弯路。

## 标题与开头

- 标题：`<模型> <序列长度> 昇腾 <卡型> 训练实践`，例如 `Qwen3.6-27B 258K 昇腾 A5 训练实践`。
- 第一段只写一句结论：卡数、开箱 → 最终的有效 TPS/卡（倍数）、峰值显存变化。例如：
  `双机 16 卡，有效 TPS/卡 54.7 → 956.4（×17.5），峰值显存 78.8 → 56.7 GiB。`

## 分类规则

- **适配问题**：跑不通、报错、结果明显错误（例如填充率异常、日志口径错）。修好之后才算“能跑”。
- **优化点**：能跑之后，改了配置或代码，吞吐、显存或稳定性发生变化。
- 一项改动如果既修了问题又带来大幅收益（例如让 packing 真正生效），在适配问题表里记现象和补丁，在优化点里记收益，并互相引用编号。

## 写法要求（去 AI 腔）

- 能用表格就用表格；正文每段不超过 3 句，每句不超过 25 字左右。
- 写具体数字和单位：`56.7 GiB`、`535.4 s`、`×2.11`，不要写“显著提升”“大幅降低”。
- 不要过程叙述和第一人称复盘：删掉“我最初以为……”“后来发现……”“这里有个方法教训”。
- 不要强调性套话：删掉“这是本次最值得记下的一条”“结论先说”“值得注意的是”“需要强调的是”“不难看出”。
- 不要总结段、“关键收获”章节。被推翻的旧结论直接不写，除非有核心价值信息可以增加到“方法论”章节。
- 如果有核心的“方法论”，可以增加此章节。
- 和本场景无关的运维经验（SSH 被封、shell 小技巧）不写进实践文档。
- 术语、参数名、文件路径、报错文本一律用代码格式。

## 输出方式

- 有 Claude Docs 连接器时，每个场景新建一篇 doc：先建骨架（标题、日期、一句结论、每节一个占位），再逐节填写。
- 没有连接器时，每个场景输出一个 Markdown 文件，文件名 `<模型>-<序列长度>-practice.md`。
